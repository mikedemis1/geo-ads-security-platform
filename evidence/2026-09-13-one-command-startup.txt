2026-09-13: GEO-ADS one-command startup, verification evidence
=================================================================

What broke during the build and what fixed it
-----------------------------------------------

Three blockers were found by review before the first build and fixed in the
Dockerfiles and dev-up.sh before anything ran:

1. backend/Dockerfile: WORKDIR /app is created owned by root. The app opens
   audit.log in that directory at import time, so uid 10001 got a
   PermissionError on start. Fix: `RUN chown app:app /app` after WORKDIR,
   before USER app.

2. .env (POSTGRES_PASSWORD) and backend/.env (DB_PASSWORD) had been generated
   separately on 2026-09-11 and held different values, so the backend could
   not authenticate against its own database. dev-up.sh now checks the two
   values match and refuses to start compose if they don't. The mismatched
   pair on this machine was deleted and regenerated as a matching pair.

3. frontend/geo-ads-frontend/Dockerfile used nginx:1.27-alpine, which starts
   as root. Switched to nginxinc/nginx-unprivileged:1.27-alpine, same nginx,
   built to run as uid 101.

What the build itself revealed, not caught by static review:

4. The container name `geo_ads_db` and host port 5433 were already taken by
   an unrelated, long-running Postgres container from a separate project
   (a university thesis, different repository, different docker-compose.yml).
   Fixed by renaming this project's db container to `geo_ads_platform_db` and
   moving its host port to 5434. No change was made to the other project or
   its data.

5. Host port 3000 was already held by a local VPN routing service, unrelated
   to Docker entirely. Moved the frontend's host port mapping to 3001. The
   container still listens on 3000 internally; nginx.conf did not need to
   change.

Dependency pinning
-------------------

backend/requirements.txt listed direct dependencies with no versions.
Captured what actually installed and built the runtime image from that
instead:

$ docker exec geo_ads_backend pip freeze > backend/requirements.lock.txt

backend/Dockerfile's build stage now installs from requirements.lock.txt.
requirements.txt stays as the short, human-readable list of direct
dependencies; requirements.lock.txt is what the build actually uses. Rebuilt
against the lock file and re-ran the verification block above a third time;
same results.

Known limits, stated plainly
------------------------------

- /health does not touch the database. A healthy /health can still sit in
  front of a backend that cannot reach Postgres. The authenticated read
  above is what actually proves the database connection and credentials
  work; making /health a real readiness check is worth doing later and is
  not part of this task.
- Base images (python:3.12-slim, node:20-alpine, postgis/postgis:16-3.4,
  nginxinc/nginx-unprivileged:1.27-alpine) are pinned by tag, not by digest.
  A rebuild months from now can pull different bytes under the same tag.
